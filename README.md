# Ranger's Rescue Route — Level 1

Solution to Level 1 of the Entelect Hackathons "Ranger's Rescue Route"
challenge: find the shortest path from `A` to `B` through a small
6-node weighted trail network using Dijkstra's algorithm.

**Result:** route `A -> D -> E -> B`, cost `9` (optimal).

## Project structure

```
.
├── data/
│   └── level1_graph.json   # graph input: adjacency list, start/end nodes
├── shortest_path.py         # generic Dijkstra implementation, reusable across levels
├── level1.py                 # loads the level 1 graph, runs the solver, writes the submission file
├── requirements.txt          # Python dependencies (currently none — stdlib only)
├── LICENSE                 # MIT
├── README.md
├── submission_l1.txt
└── .gitignore
```

### Why the split?

`shortest_path.py` doesn't know anything about "Level 1", "rangers", or
specific node names — it's a general-purpose "find the shortest path in
a weighted graph" function. `level1.py` is the thin layer on top that
knows *which* graph to load and *what to do* with the result. This
keeps the algorithm reusable if a Level 2 script is added later, since
it would only need its own runner script, not a second copy of Dijkstra.


## Running

```bash
python level1.py
```

Expected output:

```
Shortest path: A -> D -> E -> B
Total cost:    9
Wrote submission_l1.txt
```

This reads `data/level1_graph.json`, runs Dijkstra's algorithm from the
`start` node to the `end` node defined in that file, prints the route
and its cost, and writes the result to `submission_l1.txt` in the
project root.

## Input format

`data/level1_graph.json` describes the graph as an adjacency list. Each
key is a node name; each value is a list of neighbours with an edge
weight (travel time):

```json
{
  "start": "A",
  "end": "B",
  "adjacency_list": {
    "A": [{ "node": "C", "weight": 4 }, { "node": "D", "weight": 2 }],
    "B": [{ "node": "E", "weight": 4 }, { "node": "F", "weight": 7 }],
    ...
  }
}
```

The graph is undirected — every edge is listed in both directions.

## Output format

`submission_l1.txt` contains a plain-text JSON object with the route as
an ordered list of node names from start to end:

```json
{
  "route": ["A", "D", "E", "B"]
}
```

This matches the format required by the hackathon submission portal.
The portal recalculates the route's cost itself from the graph, so no
cost value is included in the file.

## How the algorithm works

`shortest_path.find_shortest_path(graph, start, end)` implements
Dijkstra's algorithm:

1. Every node starts at distance `infinity` from `start`, except
   `start` itself, which is `0`.
2. A min-heap always gives us the closest not-yet-finalised node next.
3. When we visit a node, we check every neighbour: if reaching that
   neighbour via the current node is cheaper than its previously known
   distance, we update it and record "we got here via this node".
4. This repeats until `end` is reached (or the heap is empty, meaning
   `end` is unreachable).
5. `_reconstruct_path` then walks the "got here via" links backwards
   from `end` to `start` and reverses the result into a normal
   start-to-end route.

Complexity: `O((V + E) log V)` with a binary heap, where `V` is the
number of nodes and `E` the number of edges — well within what's needed
for a graph this size (6 nodes, 9 edges).
